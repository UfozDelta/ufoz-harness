# Stage 4: Contact form

Read `../spec.md` first (Decisions, error shape apply here).

## What exists already
Product catalog (stage 2) and mock checkout (stage 3) as specified in their stage files. Keep them
working unchanged.

## Goal
A contact form: a page + API to submit a message, and a way to read back stored messages.

## DB — add one table
`contact_messages(id INTEGER PRIMARY KEY, name TEXT, email TEXT, message TEXT, created_at TEXT)`.

## API (JSON everywhere)
- `POST /api/contact` body `{"name": string, "email": string, "message": string}`. Validate in this
  order, first failure wins, 400 `{"error": "...", "field": "..."}`:
  1. `name`: trimmed, 1–100 chars → `field: "name"`.
  2. `email`: trimmed, matches `^[^\s@]+@[^\s@]+\.[^\s@]+$` → `field: "email"`.
  3. `message`: trimmed, 1–2000 chars → `field: "message"`.
  A missing field is invalid for that field. Non-object body → 400 with any `field`.
  On success, store the trimmed values (email stored as-is, not lowercased) and respond **201**
  `{"id": int, "name", "email", "message", "createdAt": ISO-8601 string}`.
- `GET /api/contact` → 200 `{"messages": [{"id","name","email","message","createdAt"}...], "count":
  int}`, newest first (ties broken by higher id first). No auth — anyone can read this, matching the
  rest of the app.

Both routes export `dynamic = "force-dynamic"`.

## Page: `/contact`
Server component shell + client form. Labelled inputs `name="name"`, `name="email"`
(`type="email"`), `name="message"` (`<textarea name="message">`). Submits with `fetch` to
`POST /api/contact`:
- Disables the submit button while the request is in flight.
- On a field error, shows the server's `error` message next to that field (e.g. in an element near
  the input containing the error text).
- On success, shows a confirmation containing `data-testid="contact-success"` and clears or hides
  the form.
- `data-testid="contact-form"` on the `<form>` element itself.

## Design
Same visual system as earlier stages (reuse `app/globals.css`, nav/footer). Apply the Design
decision from `../spec.md`. Add a nav link to `/contact` in the shared nav (`data-testid="site-nav"`
from stage 1) — e.g. `<a href="/contact">Contact</a>` — without changing the nav's existing content.

## Build rules
- `npm run build` succeeds with zero type errors. No new dependencies.
- Do not add authentication to `/api/contact` or any other route.
